Terasweep performance

Terasweep reduces repeated computation in parameter sweeps by sharing training statistics, fits and scores across trials that have the same inputs at those stages.

The two scaling studies

The original Ridge study measures successive changes to the Rust implementation, including the AVX-512 kernels. The later study holds scalar scoring fixed between Terasweep and each uncached reference, and contains measured billion-trial Terasweep runs for Ridge, DLinear, LightGBM and TiDE on an M1 Max.

The original Rust runner already shared Ridge statistics, fitted predictions and scores, applied cost factors after scoring, and recomputed details only for the winners. Profiling led first to reuse of constant paths, followed by changes to cache storage and scheduling and the introduction of two AVX-512 kernels.

The controlled comparisons measure the effect of these changes within the same runner. Comparing it with the uncached native Limen reference involves a separate timing and scoring boundary.

The merged Limen Ridge SFD delegates fitting and prediction to sklearn.linear_model.Ridge. Its training method constructs a fresh estimator and calls fit. The native UEL path repeats both preparation and model execution for each experiment row.

Return-accounting difference

Terasweep uses entry-bar open-to-close returns and multiplicative cost factors. Current native Limen uses a different entry convention and charges fees on notional. Rounded MAE and aggregate signal rates can therefore agree while returns differ. The Rust comparison retains the original scoring contract.

Ridge training statistics

Fits at different regularization strengths can share statistics computed from the training data. The solver still runs for each distinct training key.

minw,b ‖y − Xw − b1‖² + α‖w‖²

Let n be the number of training rows, d the number of features and m the number of test rows. The normal equations for Ridge without an intercept are (XᵀX + αI)w = Xᵀy, so the training data enter through two quantities.

GRAM MATRIXG = XᵀXd × d values
RIGHT-HAND SIDEh = Xᵀyd values

For each regularization strength, solve (G + αI)w = h. Since neither G nor h depends on α, the original implementation computes them once for the fixed data.

Intercept derivation

Centering gives Xc = X − 1x̄ᵀ and yc = y − ȳ1. With Gc = XcᵀXc and hc = Xcᵀyc, the centered system is (Gc + αI)w = hc and the intercept is b = ȳ − x̄ᵀw. The original code retains raw and centered statistics and accumulates the lower triangle before mirroring it for the solve.

The intercept is unpenalized. Its setting selects the appropriate stored statistics.

Size of the linear system

In the original 4,136 × 55 training matrix, the statistics retain all 55 features. Each fit solves a 55 × 55 system, whose full FP64 Gram matrix occupies 24,200 bytes (55 × 55 × 8).

Cholesky factors the system matrix as A = LLᵀ, after which forward and backward substitution recover the coefficients. The implementation uses this decomposition for each training key and shares neither an explicit inverse nor an eigendecomposition across regularization strengths.

Dependencies of the statistics

A change to the feature set, scaler, split, window, target or dataset changes the data from which the statistics are formed.

Terasweep’s solver_eps is a Cholesky pivot cutoff, whereas sklearn’s tol concerns its iterative solvers. A failed solve is retained as a failed configuration.

Reuse of fitted predictions

After a successful fit, the original code computes predictions and MAE in one pass and stores them under (alpha.to_bits(), fit_intercept, solver_eps.to_bits()). Fees and thresholds enter downstream of that key.

The expression gives leading-order work for statistics, U distinct solves and their test predictions. It excludes parsing, allocations, failure branches, scoring and reporting.

Reuse in one million sampled rows

The canonical million-row sample contained 728,102 valid rows and 271,898 failed-fit rows. Its 648,130 distinct valid base-score keys required an initial computation each, so 79,972 valid rows, or about 11% of the valid sample, reused a base score.

Sampling with replacement

SplitMix64 derives the trial parameters from the configured seed and a mixed row ID, allowing a winning trial to be reconstructed from its ID. The configured Cartesian space has 781,088,256 logical combinations, including failures. A billion sampled rows contain repeated draws.

Failed-fit accounting

After a training key fails, downstream requests reuse that failure. These requests remain in the failed and total row counts, so sampled-row throughput includes trials that did not produce fitted models.

Cost adjustment and scoring

Terasweep retains statistics of the position path so that costs can be evaluated for several fee and slippage settings without scanning the bars again.

Position path and cost categories

The rule and threshold are applied to the prediction vector, and the previous bar’s signal determines the current position subject to tradability. Entry, continuation and exit then determine the gross return and the applicable cost category.

aₜ = 1 + rₜgross   ·   Egross = ∏ₜ aₜ

For fee f and slippage s expressed as fractions, Terasweep uses the entry and exit multipliers below.

ENTRY MULTIPLIERu = (1 − f) / (1 + s)
EXIT MULTIPLIERv = (1 − f)(1 − s)
Enet = Egross · uentries · vexits

Changing either cost changes the multipliers applied to the same path.

Moments used in the Sharpe calculation

For each of the four entry and exit categories, the scorer retains a count n꜀, a sum S꜀ = Σaₜ and a squared sum Q꜀ = Σaₜ². The multipliers are 1, u, v, uv, and the net bar return in category c is k꜀aₜ − 1.

Σrnet = Σ꜀ (k꜀S꜀ − n꜀)
Σ(rnet)² = Σ꜀ (k꜀²Q꜀ − 2k꜀S꜀ + n꜀)

Combining the category moments with the count of eligible bars yields the mean and sample variance.

Details recomputed for winners

The moments discard time order and therefore cannot recover an arbitrary drawdown path, rolling-return distribution or trade-level quantile. The runner selects rows on return, Sharpe and MAE, then recomputes the detailed backtests for those winners.

The same row can occupy more than one report slot. Selection uses rounded metrics, with ties resolved in the original order. The Rust runner emits the summary and the selected details.

Score storage and scheduling

A logical scoring key can refer to a shared constant-path result or a separately stored mixed-path result. The cache can retain every evaluated key without storing a full result for each one.

Logical keys and physical slots

In the measured build, the original BaseScore occupies 128 bytes and its key occupies 24 bytes. The compact cache maps a key to the shared all-off result, the shared all-on result or an individually stored mixed result.

Cache cardinality still counts logical keys, regardless of how many distinct payloads are stored.

LOGICAL ID → PHYSICAL PAYLOAD
0       → shared all-off BaseScore
1       → shared all-on BaseScore
2 + j   → mixed BaseScore[j]

row     → { train: u32, slot: u32 }

The payload sizes exclude metadata, optional values, capacity slack, indexing and buffers, all of which contribute to process memory.

Categorical keys and indexing

The sampler already selects ordinals in finite parameter arrays, so the normal generated-row path can carry those ordinals without hashing the floating-point values. Duplicate settings retain their original deduplication behavior, and explicit CSV plans use value-based lookups.

The implementation uses a dense index when its address space fits within 64 MiB, and a sparse map with bounded initial reservation when it does not.

Storage for scheduled row referencesROW-REFERENCE STORAGE CALCULATION

Each reference occupies 8 bytes for two u32 values. The scheduler holds at most 1,048,576 references at once. The calculation covers only the row-reference buffer.

The cache persists across blocks. Within a block, pending mixed jobs are grouped by model, then the results are reduced in the original row order so that rounded ties still favor the earliest row.

Work retained for each sampled row

The compact implementation samples the row once during planning and again during original-order reduction. Cost adjustment and winner selection also run for each row, and these operations dominate after the score cache fills.

SIMD scoring

An AVX-512 vector holds eight FP64 values. Assigning those lanes to independent scoring jobs preserves the order of operations within each job.

Time-axis grouping

Consecutive bars

Comparisons can be vectorized across consecutive bars, but the equity product and category sums are accumulated over time. Reordering those reductions can change the floating-point results.

Job-axis grouping

Independent scoring jobs

Each lane has its own threshold and signal rule for the same fitted model. A prediction and price row are broadcast to all lanes, which process the bars in sequence.

Broadcasting shares input loads while preserving chronological arithmetic. Each lane owns its category accumulators, so simultaneous updates do not require scattering into shared scalar sums or reducing across time.

Scoring states by bar and lane12-BAR ILLUSTRATIVE FIXTURE

Each column shows one independent job. The current prediction gives its signal, while the preceding signal and current tradability determine the position.

Lane occupancy in the first AVX-512 prototype

The prototype grouped jobs by model and rule, leaving many eight-lane groups partly empty. At 52.7% useful AVX-512 occupancy, the first wide kernel’s median was 83.4 ms, compared with 83.6 ms for AVX2.

Historical C prototype groupingAVX2 useful lanesAVX-512 useful lanesAVX-512 median
Same model, same rule73.9%52.7%83.4 ms
Same model, mixed rules94.5%88.3%60.3 ms

Grouping on model alone increased lane occupancy by allowing different rules in the same vector. A per-lane sign transform handles less-than rules, an absolute-value mask handles absolute rules, and an inclusive mask adds equality cases. The integrated Rust kernel uses those operations.

C prototype and Rust implementation

The early x86 environment had C compilers and lacked a Rust toolchain, so the exploratory kernel was written in C and checked separately against the original Rust scorer on the Mac. Those timings cover the kernels. The integrated runner uses Rust std::arch::x86_64 intrinsics and contains no C scoring implementation.

Build and dispatch requirements

The integrated AVX-512 build targets x86-64 Linux with Rust 1.89 or later. The original ARM64 Mac cannot execute it natively. At runtime the selected AVX-512 levels require AVX-512F, and the assembly path also requires BMI1. Unsupported selections fail and the Linux assembly ABI has no port to x86 macOS or Windows.

CHECK YOUR MODEL

Why allow different rules within a same-model SIMD batch?

Mixed-rule groups fill more lanes while preserving the requested jobs and their trading convention, since the lanes still share one fitted model.

Handwritten AVX-512

Handwritten AVX-512 reduced the median standalone kernel time relative to tuned intrinsics. The difference was smaller in the complete process, where scoring occupied a small share of the time at one billion sampled rows.

Intrinsics reference

The initial handwritten variant ran faster than the first intrinsics implementation, but further tuning recovered much of the gap. The standalone study compared several intrinsics formulations under GCC and Clang and used the fastest tested formulation as its reference.

Register use and instruction order

The assembly assigns vector accumulators and keeps the position-state masks in 32-bit general-purpose registers, from which it transfers them into the AVX-512 mask registers. It schedules Boolean operations alongside accumulation and preserves separate multiplication and addition in chronological order within each lane. It uses the same precision and does not substitute FMA or use fast-math.

Timed work

Score-cache saturation




Each of the 1,677 successful training keys has 2,006 rule and threshold combinations (4 × 401 + 2 × 201), for 3,364,062 possible valid base-score keys. The 100m sample reaches that ceiling. At one billion rows, about 99.54% of valid rows reuse a base score.
